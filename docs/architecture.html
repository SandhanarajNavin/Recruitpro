Recruitment Agent

Layer encoding

Candidate layer — persistent, built once, JD-independent
Recruitment layer — per screening run, job-specific

01

Candidate intelligence is built independently of any job description

This is the load-bearing decision in the whole design. A resume is never parsed, filtered, or embedded with respect to a JD. Ingestion and screening are two separate workflows that meet at exactly one surface: the candidate repository.

The consequence is what makes the product work at all. A recruiter who has accumulated a thousand resumes over eight months does not re-process anything to open a new role — they paste a job description and query intelligence that already exists. If the two layers were coupled, every new JD would mean re-reading every resume, and cost would scale with the product of resumes and roles rather than their sum.

Rule

A resume must never be embedded or stored according to a JD filter. If a change would make ingestion depend on a job, it belongs in the recruitment layer instead.

02

System architecture

One Next.js client, one modular FastAPI application, three stores, and a worker pool. AI providers are called only from workers — never from a request handler on the critical path.

Backend module layout

The FastAPI application stays modular so components can be extracted into services later without a rewrite. Routers hold no business logic; services own orchestration; the ai/ package is the only place that knows a provider exists.

04

Resume ingestion

Upload returns in milliseconds. Everything that can fail slowly — extraction, LLM parsing, embedding — happens on a worker, behind a status the UI can poll.

The boundary matters for more than latency. A worker task can be retried, rate-limited, and made idempotent; a request handler holding an LLM call cannot. It also means a provider outage degrades ingestion into a backlog rather than a wall of failed uploads.

Retain, don't overwrite

New uploads for a known candidate create a new resume version rather than replacing the file. That keeps screening decisions auditable against the document they were made from, and lets you re-run extraction and embedding when the parsing or embedding model changes.

05

Data model

Candidate-side entities are permanent and grow by version. Job-side entities are per-role, and a screening is a single immutable run against them — re-running a job produces a new screening, not an edit.

06

Matching and ranking

Do not ask an LLM to pick five candidates out of a thousand. Narrow the field with cheap, fast filters, spend the expensive reasoning on a small set, and let deterministic code do the final ordering.

The funnel is what keeps this affordable. Each stage is cheaper per candidate than the one after it and more selective than the one before, so the LLM — the only component whose cost is measured in cents rather than microseconds — sees a bounded number of candidates no matter how large the repository grows.

Why each stage exists

  • Hard filters remove candidates no score should rescue — a missing non-negotiable skill or an unmet location constraint. Cheap, and it keeps the ANN search honest.
  • ANN retrieval catches paraphrase and adjacency that keyword matching misses, at a cost of roughly one index scan.
  • Reranking fixes the known weakness of embedding retrieval: a single vector per candidate blurs detail, while a cross-encoder reads the JD and the candidate together.
  • Evaluation produces the per-requirement verdicts and quotes that the score and the explanation are both built from.

07

Scoring and explainability

The LLM never assigns the overall percentage. It supplies evidence; application logic turns evidence into a number using weights you can read, print, and defend.

This split is what makes the score reproducible. Given the same evidence, the same weights produce the same score every time — so when a hiring manager asks why one candidate outranked another, the answer is arithmetic over cited evidence rather than a model's mood.

Why match

  • Required skills found, with the line of the resume they came from
  • Relevant experience meets or exceeds the requirement
  • Responsibilities and projects that align with the role
  • Preferred skills present

Why not — gaps

  • Required skills not found anywhere in the profile
  • Experience below the stated requirement
  • Preferred skills missing
  • Evidence unclear or insufficient to judge

Non-negotiable

The explanation model receives structured evaluation evidence and nothing else. It must not invent qualifications, experience, certifications, or skills — and the fourth gap category exists so that "we could not tell" is a first-class answer instead of a guess.

08

API surface

Two long-running operations — upload and screening — both follow the same shape: accept, return an id, expose status, serve results separately.

Method & endpointPurpose
POST /api/v1/auth/loginRecruiter authentication
POST /api/v1/resumes/uploadUpload one or more resumes — returns 202 and ids
GET /api/v1/resumes/{id}/statusIngestion progress and failure reason
GET /api/v1/candidatesSearch and list the candidate repository
GET /api/v1/candidates/{id}Profile, resume versions, parsed detail
POST /api/v1/jobsCreate a recruitment from a JD — parses requirements
GET /api/v1/jobs/{id}Job with its structured requirements
POST /api/v1/screeningsStart a matching run for a job — returns 202
GET /api/v1/screenings/{id}Screening status and stage
GET /api/v1/screenings/{id}/resultsRanked candidates, score breakdown, explanations

The Next.js client generates its types from the FastAPI OpenAPI schema, so a contract change surfaces as a TypeScript error rather than a runtime surprise.

09

Trust boundaries

Resumes are among the most sensitive documents a company holds. Nothing in the data tier is reachable from the public internet, and every AI provider connection is outbound-only.

Controls

  • HTTPS everywhere; encryption at rest and in transit
  • Validate file type and size, then malware-scan before processing
  • Role-based access control for recruiter and admin
  • Audit log for every screening decision and override

Fairness and retention

  • Protected characteristics excluded from ranking inputs
  • Recruiters can review and override every AI recommendation
  • Defined retention and deletion policy per candidate
  • Screening results are immutable, so a decision stays reconstructible

10

Decisions, and what is deliberately out of V1

Every item excluded here has a clear path in. The point of V1 is to avoid paying for flexibility before there is anything to flex.

QuestionV1 decisionReason
Vector storagepgvector inside PostgresThis is a relational candidate-management app that also needs semantic search. One database means SQL filters compose with vector similarity in a single query, and transactions stay simple. Move to a dedicated vector DB when scale — not taste — demands it.
LangChainNot requiredDirect provider calls and plain Python services cover the whole deterministic pipeline without a framework's abstractions in the way.
LangGraphNot requiredThe V1 flow is a predictable workflow, not an autonomous agent. Introduce it when the product genuinely needs branching, human approval gates, and long-running stateful runs.
Kubernetes / microservicesExcludedOperational cost with no V1 benefit. The FastAPI app stays modular so components can be extracted later.
Scoring weightsConfig, fixed per deploymentConfigurable weights are a product feature that needs a UI, an audit trail, and per-job overrides. Ship the mechanism first.

Where it goes next

  • Recruiter-configurable scoring weights, per job and per organization
  • Candidate deduplication and identity resolution across resume versions
  • Interview question generation and candidate comparison workflows
  • Advanced reranking, plus ranking-quality monitoring against recruiter overrides
  • A stateful agent layer — the point at which LangGraph starts to earn its place

The architecture in one line

Upload once → build candidate intelligence → store in a reusable repository → match against any future JD → retrieve → rerank → evaluate → score → explain.
